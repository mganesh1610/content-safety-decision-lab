# Launch review and experiment plan

This document specifies a proposed product experiment. No product launch, user randomization, causal reduction or moderation deployment has occurred.

1. Product defines the MVP action: a scored review queue with human decisions. Policy writes the harm taxonomy, ambiguous-label examples and appeal rules. Operations supplies reviewer capacity and welfare practices. Engineering implements stable assignment, score logging and rollback. Data science owns metric definitions, sample size, randomization diagnostics and analysis.
2. Begin with shadow scoring. Review threshold stability and the capacity frontier. Inspect errors with minimum necessary exposure to source content. Escalate disagreements rather than treating an annotation as an unquestionable policy verdict.
3. The future experiment randomizes users, retains all assigned users for intention-to-treat analysis, clusters uncertainty by user, and checks sample-ratio mismatch before outcome analysis. Avoid assignment by post when users generate multiple correlated observations. Freeze the primary metric, analysis window and sequential monitoring rule before launch.
4. Primary metric: independently audited violating exposures per eligible user. Guardrails: false positive action rate on an independently adjudicated sample, creator appeal overturn rate, reviewer queue age/capacity, creator retention and user engagement. Log each denominator and missing-data rate. Do not use the historical corpus prevalence as live prevalence.
5. Illustrative planning inputs in `results/metrics.json`: assumed 1% baseline user harm rate, a 0.2 percentage point absolute reduction, two-sided alpha .05, 80% power, 50/50 assignment, independent-user approximation. The normal-approximation calculation returns users per arm. Inputs are assumptions and must be replaced with approved shadow measurements; account for clustering and multiple comparisons before launch.
6. A release reviewer checks data coverage, policy approval, capacity, precision/recall intervals, observed guardrail limits and rollback readiness. A descriptive offline score does not satisfy these gates. Keep the model in shadow mode until real operational prerequisites are met.

Root-cause questions: Is a review-rate change driven by source mix, text length, data loss, annotation drift or a new score distribution? Reconcile event counts and denominators first. Compare stable cohorts and overlapping slices carefully; investigate label disagreements and threshold effects before changing enforcement.
